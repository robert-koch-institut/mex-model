# Entity conventions

Both the Extracted and Merged variants share the same set of descriptive properties. The Extracted variant additionally carries the four mandatory provenance properties (`identifier`, `hadPrimarySource`, `identifierInPrimarySource`, `stableTargetId`), while the Merged variant carries only `identifier` alongside descriptive properties. The Merged variant additionally includes `supersededBy`, which allows a deprecated or duplicate Merged entity to point to the preferred replacement.

The Merged variant is the normalised, deduplicated record that consolidates descriptions from one or more primary sources. If a Merged entity has been superseded by another, e.g. following deduplication, the `supersededBy` property will point to the preferred replacement.

## AccessPlatform

The AccessPlatform entity describes a technical system or service that provides access to distributions or resources. It corresponds to `dcat:DataService`.

### When to use

Use `AccessPlatform` to describe any technical system, API, or service through which a dataset or distribution can be accessed. For example, a REST API, a file server, a database interface, or a web portal. The entity captures both the technical characteristics of the access mechanism and the organisational responsibility for it.

`AccessPlatform` should not be confused with `Distribution`, which describes a specific representation or download of a dataset. An `AccessPlatform` is the system through which one or more distributions are made available. A `Distribution` is the artefact that is made available through it.

Use `ExtractedAccessPlatform` when ingesting access platform metadata from a primary source system via an ETL pipeline. Each extracted record represents the platform as described by that specific source, carrying the provenance properties that trace it back to its origin.

Use `MergedAccessPlatform` when referencing an access platform from another entity, or when consuming access platform metadata in the catalogue or downstream systems.

### Mandatory fields & expected values

The following properties are required on all valid instances:

| Property | Variant | Type | Expected value |
| --- | --- | --- | --- |
| identifier | Both | Identifier | Generated by MEx. Cannot be set manually. |
| technicalAccessibility | Both | Concept URI | One value from the [technical-accessibility vocabulary](https://mex.rki.de/item/technical-accessibility) |
| hadPrimarySource | Extracted only | Identifier | Reference to a MergedPrimarySource identifier |
| identifierInPrimarySource | Extracted only | String | ID of this access platform in the originating source system |
| stableTargetId | Extracted only | Identifier | Reference to the corresponding MergedAccessPlatform identifier |

All other properties are optional.

### Schema Detail

```{mex-entity} AccessPlatform
:variant: both
```

### Common pitfalls

* Confusing `AccessPlatform` with `Distribution`: a common mistake is creating an `AccessPlatform` record for each individual file or download rather than for the system that serves them. One `AccessPlatform` may serve multiple `Distribution` entities.
* Leaving `technicalAccessibility` inconsistent: marking a platform as externally accessible when it is in fact only reachable within the RKI network, or vice versa. This has downstream implications for access control and catalogue visibility.
* Omitting `unitInCharge`, when `technicalAccessibility` is "internal": while optional, this property is important for operational accountability.

## Activity

The `Activity` entity describes any activity carried out by the RKI, whether it is a funded research project, a statutory surveillance task, or any other organised undertaking. It corresponds to `prov:Activity` and serves primarily to provide contextual information for `Resource` entities.

### When to use

Use `Activity` to describe a research project, a statutory task performed under federal law, or any other organised activity conducted at the RKI. Activities provide essential context for datasets. A `Resource` can reference the `Activity` that generated it via the wasGeneratedBy property.

`Activity` should not be confused with `Resource`, which describes the data itself. An `Activity` is the process or project that produced or is associated with data. A `Resource` is the dataset that resulted from or is used within that activity.

Use `ExtractedActivity` when ingesting activity metadata from the primary source system such as a project database or HR system. Each extracted record represents the activity as described by that specific source.

Use `MergedActivity` when referencing an activity from another entity, for example when linking a `Resource` to the project that generated it, when linken an `Activity` to a succeeding activity, or when consuming activity metadata in the catalogue.

### Mandatory fields & expected values

| Property | Variant | Type | Expected value |
| --- | --- | --- | --- |
| identifier | Both | Identifier | Generated by MEx. Cannot be set manually. |
| title | Both | Array of Text | At least one value; SHOULD include both de and en |
| contact | Both | Array of Identifiers | References to one or more MergedOrganizationalUnit, or MergedContactPoint |
| responsibleUnit | Both | Array of Identifiers | References to one or more MergedOrganizationalUnit |
| hadPrimarySource | Extracted only | Identifier | Reference to a MergedPrimarySource identifier |
| identifierInPrimarySource | Extracted only | String | ID of this activity in the originating source system |
| stableTargetId | Extracted only | Identifier | Reference to the corresponding MergedActivity identifier |

### Schema Detail

```{mex-entity} Activity
:variant: both
```

### Common pitfalls

* Confusing `contact` and `responsibleUnit`: `contact` is a point of enquiry (unit, or contact point), while `responsibleUnit` specifically denotes organisational accountability. Both are mandatory and should not be used interchangeably.
* Confusing `involvedPerson` and `contact`: persons involved in carrying out the activity belong in `involvedPerson`, while `contact` is for the unit a user should reach out to with questions.
* Omitting `start` and `end`: while optional, these are important for catalogue discoverability and for understanding whether an activity is ongoing or concluded.
* Using plain strings for `theme` or `activityType`: these require Concept URIs from their respective vocabularies, not free-text values.

## BibliographicResource

The `BibliographicResource` entity describes a publication, article, report or other bibliographic output. It corresponds to `dcterms:BibliographicResource`.

### When to use

Use `BibliographicResource` to describe any publication associated with RKI research. This includes journal articles, reports, preprints, book chapters, or similar outputs. It is typically linked from an `Activity` via the `publication` property.

`BibliographicResource` should not be confused with `Resource`, which describes a dataset or data collection. A `BibliographicResource` is a published document, a `Resource` is research data.

Use `ExtractedBibliographicResource` when ingesting publication metadata from a primary source such as a publication database or repository.

Use `MergedBibliographicResource` when referencing a publication from another entity, or when consuming publication metadata in the catalogue.

### Mandatory fields & expected values

| Property | Variant | Type | Expected value |
| --- | --- | --- | --- |
| identifier | Both | Identifier | Generated by MEx. Cannot be set manually. |
| accessRestriction | Both | Concept URI | One value from the [access-restriction vocabulary](https://mex.rki.de/item/access-restriction) |
| title | Both | Array of Text | At least one value; SHOULD include both de and en |
| creator | Both | Array of Identifiers | At least one reference to a MergedPerson |
| hadPrimarySource | Extracted only | Identifier | Reference to a MergedPrimarySource identifier |
| identifierInPrimarySource | Extracted only | String | ID of this bibliographic resource in the originating source system |

### Schema Detail

```{mex-entity} BibliographicResource
:variant: both
```

### Common pitfalls

* Duplicating publications across sources: the same `publication` may be present in multiple source systems. Ensure `stableTargetId` is consistent to allow proper merging.
* Confusing `BibliographicResource` with `Resource`: a PDF report describing a dataset is a `BibliographicResource`. The dataset itself is a `Resource`.

## Consent

The `Consent` entity records a data subject's consent for the use of their personal data. It is aligned with the W3C Data Privacy Vocabulary (`dpv:Consent`).

### When to use

Use `Consent` to document GDPR-relevant consent records associated with research data. This entity is specific to the data privacy domain and is unlikely to be populated via automated extraction from most source systems.

Use `ExtractedConsent` when ingesting consent records from a primary source that manages participant consent.

Use `MergedConsent` when referencing a consent record fom another entity or consuming it downstream.

### Mandatory fields & extracted values

| Property | Variant | Type | Expected value |
| --- | --- | --- | --- |
| identifier | Both | Identifier | Generated by MEx. Cannot be set manually. |
| hasConsentStatus | Both | Concept URI | One value from [consent-status](https://mex.rki.de/item/consent-status) |
| hasDataSubject | Both | Identifier | Reference to MergedPerson (the data subject) identifier |
| isIndicatedAtTime | Both | Date-time string | RFC3339-like YYYY-MM-DDTHH:MM:SSZ (as per schema pattern) |
| hadPrimarySource | Extracted only | Identifier | Reference to MergedPrimarySource identifier |
| identifierInPrimarySource | Extracted only | String | ID in primary source (1–1000 chars; no newline) |
| stableTargetId | Extracted only | Identifier | Reference to the corresponding MergedConsent identifier |

### Schema Detail

```{mex-entity} Consent
:variant: both
```

### Common pitfalls

* Conflating consent status with access restriction: consent is a GDPR-compliant declaration of a data subject's (an instance of `Person`) declaration. Access restriction on a `BibliographicResource`, `Resource` or `Distribution` indicates an access level of a resource or technical system. These are distinct and should not substitute for one another.
* Conflicting `Consent` items: For every person item, there is a corresponding consent item. When person items are extracted from various primary source systems, duplicates of person items may occur. These may also have conflicting consent statuses. These items cannot be merged. For detailed information on the concept of GDPR-compliant consents, see Chapter XX. <PLACE CORRECT CHAPTER HERE>

## ContactPoint

The `ContactPoint` entity represents a shared email address or contact channel for a team or organisational function. It corresponds to `vcard:Kind`.

### When to use

Use `ContactPoint` when a contact for an entity is a shared functional address, such as a team inbox, rather than an individual person. It provides a stable point of contact that does not depend on a specific individual remaining in post.

`ContactPoint` should not be confused with `Person`, which represents an individual. If a named individual is mentioned, use a reference to a `MergedPerson`. If the contact is a role-based or shared address, use `ContactPoint`.

Use `ExtractedContactPoint` when ingesting contact point metadata from a primary source system.

Use `MergedContactPoint` when referencing a contact point from another entity such as an `Activity` or `Resource`.

### Mandatory fields & expected values

| Property | Variant | Type | Expected value |
| --- | --- | --- | --- |
| identifier | Both | Identifier | Generated by MEx. Cannot be set manually. |
| email | Both | Array of strings | At least one valid email address (minItems: 1)
| hadPrimarySource | Extracted only | Identifier | Reference to MergedPrimarySource identifier |
| identifierInPrimarySource | Extracted only | String | ID of the contact point in the originating source system (1–1000 chars; no newline) |
| stableTargetId | Extracted only | Identifier | Reference to MergedContactPoint identifier |

### Schema Detail

```{mex-entity} ContactPoint
:variant: both
```

### Common pitfalls

* Using a personal mail address as a `ContactPoint`: `ContactPoint` should always reference group or functional mail addresses.

## Distribution

The `Distribution` entity describes a specific representation or downloadable form of a dataset. It corresponds to `dcat:Distribution`.

### When to use

Use `Distribution` to describe a specific file, format, or access form of a Resource, for example a CSV file, an API response, or a ZIP archive. A single Resource may have multiple `Distribution` items, one per format or access method.

`Distribution` should not be confused with `AccessPlatform`. A `Distribution` is the artefact, the specific file or data representation. An `AccessPlatform` is the system through which it is served.

Use `ExtractedDistribution` when ingesting distribution metadata from a primary source system.

Use `MergedDistribution` when referencing a distribution from a Resource or consuming distribution metadata in the catalogue or downstream systems.

### Mandatory fields & expected values

| Property | Variant | Type | Expected value |
| --- | --- | --- | --- |
| identifier | Both | Identifier | Generated by MEx. Cannot be set manually. |
| accessRestriction | Both | Concept URI | One value from [access-restriction vocabulary](https://mex.rki.de/item/access-restriction) |
| title | Both | Array of Text | At least one value (minItems: 1) |
| issued | Both | Date string | One of the allowed date formats (year / year-month / year-month-day / year-month-day-time) per schema patterns |
| hadPrimarySource | Extracted only | Identifier | Reference to MergedPrimarySource identifier |
| identifierInPrimarySource | Extracted only | String | ID of this distribution in the originating source system (1–1000 chars; no newline) |
| stableTargetId | Extracted only | Identifier | Reference to MergedDistribution identifier |

### Schema Detail

```{mex-entity} Distribution
:variant: both
```

### Common pitfalls

* Creating one `Distribution` per dataset instead of per format: if a dataset is available in three formats, three `Distribution` records should exist, not one.
* Confusing `accessURL` and `downloadURL`: `accessURL` points to a page where the distribution can be accessed. `downloadURL` points directly to the downloadable file. Both may be present simultaneously

## Organization

The `Organization` entity describes an external institution, a legal or administrative body outside the RKI. It corresponds to `foaf:Organization`.

### When to use

Use `Organization` to represent an external institution, for example a funding body, a cooperating university, or an international partner organisation.

`Organization` should thus not be confused with `OrganizationalUnit`, which represents departments and units within the RKI. If the entity is part of the RKI, use `OrganizationalUnit`. If it is an external body, use `Organization`.

Use `ExtractedOrganization` when ingesting external organisation metadata from a primary source, for example from Wikidata.

Use `MergedOrganization` when referencing an external organisation from another entity, such as the `funderOrComissioner` or `externalAssociate` of an `Activity`.

### Mandatory fields & expected values

| Property | Variant | Type | Expected value |
| --- | --- | --- | --- |
| identifier | Both | Identifier | Generated by MEx. Cannot be set manually. |
| officialName | Both | Array of Text | At least one value (minItems: 1) |
| hadPrimarySource | Extracted only | Identifier | Reference to MergedPrimarySource identifier |
| identifierInPrimarySource | Extracted only | String | ID of this organization in the originating source system (1–1000 chars; no newline) |
| stableTargetId | Extracted only | Identifier | Reference to MergedOrganization identifier |

### Schema Detail

```{mex-entity} Organization
:variant: both
```

### Common pitfalls

* Using `Organization` for RKI units: internal RKI departments and units must be modelled as `OrganizationalUnit`, not `Organization`
* Duplicating organisations across sources: the same external institution may appear in multiple source systems under slightly different names. Authority file identifiers (ROR, GND) should be used to enable deduplication.

## OrganizationalUnit

The `OrganizationalUnit` entity represents a department, team, or administrative unit within the RKI. It corresponds to `org:OrganizationalUnit`.

### When to use

Use `OrganizationalUnit` to represent any internal RKI structural unit: a department, a reference centre, a working group, or a project team. Organisational units can be arranged in a hierarchy using the `parentUnit` and `unitOf` properties.

`OrganizationalUnit` should not be confused with `Organization`, which represents external institutions. If the body is part of the RKI, use `OrganizationalUnit`.

Use `ExtractedOrganizationalUnit` when ingesting unit metadata from a primary source such as a database or organisational directory.

Use `MergedOrganizationalUnit` when referencing an RKI unit from another entity, for example as the `responsibleUnit` of an `Activity` or the `unitInCharge` of an `AccessPlatform`.

### Mandatory fields & expected values

| Property | Variant | Type | Expected value |

| identifier | Both | Identifier | Generated by MEx. Cannot be set manually. |
| name | Both | Array of Text | At least one value (minItems: 1) |
| hadPrimarySource | Extracted only | Identifier | Reference to MergedPrimarySource identifier |
| identifierInPrimarySource | Extracted only | String | ID of this organization in the originating source system (1–1000 chars; no newline) |
| stableTargetId | Extracted only | Identifier | Reference to MergedOrganizationalUnit identifier |

### Schema Detail

```{mex-entity} OrganizationalUnit
:variant: both
```

### Common pitfalls

* Confusing `OrganizationalUnit` with `Organization`: a recurring error, particularly for units with close external partnerships. The rule is simple: if it is part of the RKI, it is an `OrganizationalUnit`.
* Not modelling the hierarchy: `parentUnit` and `unitOf` should be populated where the organisational hierarchy is known, as this is important for catalogue navigation.

## Person

The `Person` entity represents an individual researcher, staff member, or named contact associated with RKI activities or resources. It corresponds to `foaf:Person`.

### When to use

Use `Person` to represent a named individual, for example a person involved in an activity, a dataset contributor, or a publication author. Person records are typically sourced from HR or directory systems and enriched with authority identifiers such as ORCID.

Person should not be confused with `ContactPoint`, which represents a shared functional address rather than an individual. If the contact is role-based or shared, use `ContactPoint`. if it is a specific named person, use `Person`.

Use `ExtractedPerson` when ingesting person metadata from a primary source.

Use `MergedPerson` when referencing an individual from another entity, for example as the `involvedPerson` of a project.

### Mandatory fields & expected values

| Property | Variant | Type | Expected value |
| --- | --- | --- | --- |
| identifier | Both | Identifier | Generated by MEx. Cannot be set manually. |
| hadPrimarySource | Extracted only | Identifier | Reference to a MergedPrimarySource identifier. |
| identifierInPrimarySource | Extracted only | String | ID of this person in the originating source system |
| stableTargetId | Extracted only | Identifier | Reference to the corresponding MergedPerson identifier |

### Schema Detail

```{mex-entity} Person
:variant: both
```

### Common pitfalls

* Referencing persons by `name` string instead of `identifier`: all references to persons in other entities must use the `MergedPerson` identifier, not a name string.
* Creating duplicate person records: the same individual may appear in multiple source systems. Authority identifiers (ORCID) should be used to support deduplication. Take care identifying different persons carrying the same name.
* Confusing `Person` with `ContactPoint`: see decision guide above

## PrimarySource

The `PrimarySource` entity represents a source system from which metadata is extracted and loaded into MEx. It corresponds to `prov:PrimarySource` and is a foundational provenance concept. Every Extracted entity references a `MergedPrimarySource` via `hadPrimarySource`.

### When to use

Use `PrimarySource` to describe a system, database, or API that feeds metadata into MEx via an extractor pipeline.

`PrimarySource` is a technical provenance entity and is established when a new extractor pipeline is set up and registered in the system.

Use `ExtractedPrimarySource` when registering a new source system in MEx.

Use `MergedPrimarySource` when referencing the origin of an extracted record. This is the value supplied in the `hadPrimarySource` property of every Extracted entity.

### Mandatory fields & expected values

| Property | Variant | Type | Expected value |
| --- | --- | --- | --- |
| identifier | Both | Identifier | Generated by MEx. Cannot be set manually. |
| hadPrimarySource | Extracted only | Identifier | Self-referential for the MEx system's own primary source record |
| identifierInPrimarySource | Extracted only | String | ID of this primary source in the originating source system |
| stableTargetId | Extracted only | Identifier | Reference to the corresponding MergedPrimarySource identifier |

### Schema Detail

```{mex-entity} PrimarySource
:variant: both
```

### Common pitfalls

* Confusing `PrimarySource` with the extracted entities it produces: the `PrimarySource` describes the system, not the data it contains.
* Confusing `PrimarySource` with `AccessPlatform`: Whilst a `PrimarySource` can also be an `AccessPlatform`, an `AccessPlatform` is not necessarily the primary source for MEx metadata. A `PrimarySource` is a specific type of data service for MEx that serves as the sole source for metadata extraction. An `AccessPlatform` is used in conjunction with a user-side data service. It may be the case that the system used to access the data and the primary source for metadata extraction are one and the same, but even in this instance there would be two separate elements: a `PrimarySource` and an `AccessPlatform`.
* Leaving `hadPrimarySource` self-referential without documentation: the MEx system itself is its own primary source for `PrimarySource` records. This should be clearly documented in pipeline configurations.

### Resource

The `Resource` entity is the central entity of the MEx model. It describes a dataset, data collection, or other research data asset. It corresponds to `dcat:Dataset`.

### When to use

Use `Resource` to describe any research dataset or data collection produced or managed by the RKI, e.g. surveillance data, study data, registry data, or any other structured data asset. Resources are the central objects of discovery in the metadata catalogue.

A `Resource` describes the dataset as a whole. Its individual access forms or file representations are described as `Distribution` entities. The project or activity that produced it is described as an `Activity` linked via `wasGeneratedBy`. Individual data variables within it may be described as Variable entities.

Use `ExtractedResource` when ingesting dataset metadata from a primary source system such as a data repository or research database.

Use `MergedResource` when referencing a dataset from another entity, or when consuming dataset metadata in the catalogue.

### Mandatory fields & expected values

| Property | Variant | Type | Expected value |
| --- | --- | --- | --- |
| identifier | Both | Identifier | Generated by MEx. Cannot be set manually. |
| accessRestriction | Both | Concept URI | One value from [access-restriction vocabulary](https://mex.rki.de/item/access-restriction) |
| title | Both | Array of Text | At least one value (minItems: 1) |
| theme | Both | Array of Concept URIs | At least one value (minItems: 1) from [theme vocabulary](https://mex.rki.de/item/theme) |
| contact | Both | Array of identifiers | At least one reference to MergedOrganizationalUnit, or MergedContactPoint (minItems: 1) |
| unitInCharge | Both | Array of identifiers | At least one reference to MergedOrganizationalUnit (minItems: 1) |
| hadPrimarySource | Extracted only | Identifier | Reference to MergedPrimarySource identifier |
| identifierInPrimarySource | Extracted only | String | ID of this resource in the originating source system (1–1000 chars; no newline) |
| stableTargetId | Extracted only | Identifier | Reference to MergedResource identifier |

### Schema Detail

```{mex-entity} Resource
:variant: both
```

### Common pitfalls

* Confusing `Resource` with `Distribution`: the `Resource` is the abstract dataset. `Distribution` describes its concrete representations. A `Resource` without any `Distribution` is valid but may limit discoverability.
* Confusing `Resource` with `BibliographicalResource`: a publication about a dataset is a `BibliographicResource`. The dataset itself is a `Resource`.

## ResourceSeries

The `ResourceSeries` entity describes a collection of resources that are published separately but share characteristics that group them, such as a recurring surveillance report or a longitudinal study with annual data releases. It corresponds to `healthdcat:DatasetSeries`.

### When to use

Use `ResourceSeries` to represent a named series of related datasets that are released over time or in parts. For example, a weekly epidemiological bulletin where each edition is its own `Resource`, or a multi-wave survey where each wave produces a separate dataset.

`ResourceSeries` should not be confused with `Resource`, which describes a single dataset. A `ResourceSeries` is the umbrella that groups multiple `Resource` entities. It should also not be confused with `VariableGroup`, which groups variables within a single resource rather than grouping resources together.

Use `ExtractedResourceSeries` when ingesting series metadata from a primary source system.

Use `MergedResourceSeries` when referencing a series from another entity or consuming series metadata in the catalogue.

### Mandatory fields & expected values

| Property | Variant | Type | Expected value |
| --- | --- | --- | --- |
| identifier | Both | Identifier | Generated by MEx. Cannot be set manually. |
| title | Both | Array of Text | At least one value (minItems: 1); SHOULD include both `de` and `en` |
| description | Both | Array of Text | At least one value (minItems: 1) |
| hadPrimarySource | Extracted only | Identifier | Reference to a MergedPrimarySource identifier |
| identifierInPrimarySource | Extracted only | String | ID of this resource series in the originating source system (1–1000 chars; no newline) |
| stableTargetId | Extracted only | Identifier | Reference to the corresponding MergedResourceSeries identifier |

All other properties are optional.

### Schema Detail

```{mex-entity} ResourceSeries
:variant: both
```

### Common pitfalls

* Confusing `ResourceSeries` with `Resource`: a `ResourceSeries` never describes data directly, it groups `Resource` entities. If the thing you are describing has distributions, variables, or access restrictions of its own, it is a `Resource`, not a `ResourceSeries`.
* Not linking Resources to their series: a `ResourceSeries` is only useful if individual `Resource` entities reference it. Ensure the relationship is established from the resource side.
* Omitting `start`/`end`: while optional, temporal coverage helps catalogue users understand whether the series is ongoing or concluded and what time span it covers.
* Using `ResourceSeries` for one-off collections: if a group of datasets was released once and will not grow, consider whether a single `Resource` with multiple `Distribution` records is more appropriate.

## Variable

The `Variable` entity describes a single data variable within a resource, for example a column in a dataset or a field in a data dictionary. It is MEx-specific with no direct DCAT equivalent. It corresponds to `CSVW` in HealthDCAT-AP.

### When to use

Use `Variable` to describe individual fields or variables within a `Resource`, particularly where variable-level documentation is meaningful for data reuse, for example coded variables, measurement units, or variables with complex value ranges.

`Variable` should not be confused with `VariableGroup`, which is a logical grouping of multiple variables. A `Variable` is the individual field. A `VariableGroup` is the container that organises related variables.

Use `ExtractedVariable` when ingesting variable-level metadata from a data dictionary or codebook in a primary source system.

Use `MergedVariable` when referencing a variable from another entity or consuming variable metadata in the catalogue's dedicated variable search view.

### Mandatory fields & expected values

| Property | Variant | Type | Expected value |
| --- | --- | --- | --- |
| identifier | Both | Identifier | Generated by MEx. Cannot be set manually. |
| label | Both | Array of Text | At least one value (minItems: 1) |
| usedIn | Both | Array of identifiers | At least one reference to MergedResource (minItems: 1) |
| hadPrimarySource | Extracted only | Identifier | Reference to MergedPrimarySource identifier |
| identifierInPrimarySource | Extracted only | String | ID of this variable in the originating source system (1–1000 chars; no newline) |
| stableTargetId | Extracted only | Identifier | Reference to MergedVariable identifier |

### Schema Detail

```{mex-entity} Variable
:variant: both
```

### Common pitfalls

* Confusing `Variable` with `VariableGroup`: individual fields belong in `Variable`. Use `VariableGroup` only to group related variables logically.
* Not linking variables to their resource: a `Variable` should reference its parent `Resource` to be meaningful in the catalogue context.

## VariableGroup

The `VariableGroup` entity represents a logical grouping of `Variable` entities within a Resource, for example a section of a questionnaire or a thematic cluster of variables in a dataset. It is MEx-specific with no direct DCAT equivalent.

### When to use

Use `VariableGroup` when variables within a `Resource` can be meaningfully organised into named groups, e.g. by instrument section, dataset table, topic, or measurement domain. It is optional and should only be used where grouping genuinely aids understanding of the dataset structure.

`VariableGroup` should not be confused with `Variable`. A `VariableGroup` is the container. Individual fields belong in `Variable` entities that reference the group.

Use `ExtractedVariableGroup` when ingesting grouping structure from a data dictionary or codebook in a primary source system.

Use `MergedVariableGroup` when referencing a variable group from another entity or consuming variable group metadata in the catalogue.

### Mandatory fields & expected values

| Property | Variant | Type | Expected value |
| --- | --- | --- | --- |
| identifier | Both | Identifier | Generated by MEx. Cannot be set manually. |
| label | Both | Array of Text | At least one value (minItems: 1) |
| containedBy | Both | Array of identifiers | At least one reference to MergedResource (minItems: 1) |
| hadPrimarySource | Extracted only | Identifier | Reference to MergedPrimarySource identifier |
| identifierInPrimarySource | Extracted only | String | ID of this variable in the originating source system (1–1000 chars; no newline) |
| stableTargetId | Extracted only | Identifier | Reference to MergedVariableGroup identifier |

### Schema Detail

```{mex-entity} VariableGroup
:variant: both
```

### Common pitfalls

* Creating `VariableGroup`s without `Variable`s: a group with no member variables provides no value. Ensure that `Variable` entities reference their parent group.
* Over-grouping: not every dataset requires variable groups. Only introduce grouping where it reflects a genuine and meaningful structure in the source data.
