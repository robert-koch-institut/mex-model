# Maintaining the specification

This chapter describes how the specification is kept consistent with the MEx model. It is primarily addressed to developers who change schemas, vocabularies or the documentation toolchain. Metadata specialists will find the checklists for content changes in the section [Checklists for model changes](#checklists-for-model-changes).

## Principles

The maintenance of the specification follows four principles:

* The schemas are the source of truth. The JSON Schema files in `mex/model` define the model. The specification is derived from them and must never contradict them. If the specification and a schema disagree, the schema is correct and the specification has to be fixed.
* Generate rather than copy. Every piece of information that can be read from the repository is rendered at build time by a Sphinx extension. Content is only written by hand where it cannot be derived, for instance explanations, design decisions and conceptual mappings.
* One release, one specification. The published specification is built from a release tag. It therefore always describes exactly one released version of the model.
* A clean build is mandatory. The documentation build must not produce a single Sphinx warning. A broken cross-reference, a missing schema file or an unknown vocabulary identifier fails the test suite.

## Documentation toolchain

### Build configuration and extensions

The specification is built with Sphinx and the MyST parser. All pages are written in MyST markdown. The configuration and the custom extensions are located in the `docs` directory:

| File | Purpose |
| --- | --- |
| `docs/conf.py` | Sphinx configuration: extensions, MyST settings (`colon_fence`, `fieldlist`, `deflist`, heading anchors up to level 3) and HTML theme |
| `docs/_ext/mex_schema.py` | Provides the directives `{mex-entity}` and `{mex-field}`. Both delegate to the `jsonschema` directive of sphinx-jsonschema. |
| `docs/_ext/jsonschema_patches.py` | Adjusts how sphinx-jsonschema renders MEx schemas: adds a `useScheme` row with a link to the vocabulary, renders `default` and `pattern` as inline code, converts `:ref:` roles to MyST syntax and folds the `supersededBy` condition of Merged schemas into a readable note |
| `docs/_ext/mex_example.py` | Provides the directive `{mex-example}`. Generates an artificial Merged item with `mex-artificial` or reads a concept or concept scheme from the local vocabularies. |
| `docs/_ext/vocabularies.py` | Provides the directive `mexvocabularies`. Renders one section with a concept table per vocabulary and registers the concept scheme identifiers as link targets for `useScheme`. |
| `docs/_static/custom.css` | Style adjustments of the HTML output |

The directives are used as follows:

````markdown
```{mex-entity} Resource
```

```{mex-field} identifier
```

```{mex-example} Resource
```

```{mex-example} Concept
:identifier: https://mex.rki.de/item/health-category-16
```

```{eval-rst}
.. mexvocabularies:: ../mex/model/vocabularies
```
````

Entity names are written in CamelCase and converted to kebab-case file names, e.g. `AccessPlatform` resolves to `extracted-access-platform.json` and `merged-access-platform.json`. If no `extracted-` file exists, the directive renders the single schema file of the entity (e.g. `concept.json`). Field names are converted to lower case and resolved to `mex/model/fields/<name>.json`.

### Quality gates

Changes are checked automatically at several points:

| Check | Where it runs | What it covers |
| --- | --- | --- |
| pre-commit hooks | locally on commit and in the linting workflow (`linting.yml`) | ruff, JSON formatting, YAML syntax, linting of the translation files (`.po`), mypy for `mex`, `tests`, `scripts` and `docs`, schema checks via `scripts/check_schemas.py` |
| Test suite | testing workflow (`testing.yml`) on every pull request, for all supported Python versions | Schema syntax, field validation, vocabularies, translations, consistency between Extracted and Merged schemas, identical declaration of properties with the same name across entities, the `supersededBy` condition, the Sphinx extensions and a full documentation build without warnings |
| Changelog check | reviewing workflow (`reviewing.yml`) on every pull request | Fails if `CHANGELOG.md` was not modified |

Locally, the same checks are run with `make lint` and `make test`. The specification is built with `make docs`, the output is written to `docs/dist`.

## Change workflow

Every change to the model or the specification follows the same workflow:

1. Create a feature branch from `main`.
2. Change the schemas, vocabularies or documentation.
3. Update all manually maintained content that is affected by the change (see [Checklists for model changes](#checklists-for-model-changes)).
4. Add an entry to `CHANGELOG.md` in the appropriate section of the unreleased version. The changelog follows [Keep a Changelog](https://keepachangelog.com/en/1.0.0/), the project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
5. Open a pull request. An assignee is added automatically, linting, tests and the changelog check run on every push.
6. After review and approval, merge the pull request into `main`. The `main` branch is mirrored automatically to [OpenCoDE](https://gitlab.opencode.de/robert-koch-institut/mex/mex-model).
7. To publish a release, a maintainer starts the release workflow (`release.yml`) manually and selects `major`, `minor` or `patch`. The workflow runs `mex release`, creates the tag, publishes the package to PyPI, signs the artifacts and creates a GitHub release.
8. The new tag triggers the documentation workflow (`documentation.yml`), which builds the specification and deploys it to [GitHub Pages](https://robert-koch-institut.github.io/mex-model/).

Changes merged into `main` are not visible in the published specification until the next release.

## Checklists for model changes

Each checklist distinguishes between content that is updated automatically and content that has to be updated by hand in the same pull request.

### Adding or changing an entity

Updated automatically:

* Schema tables in [Entity conventions](entity-conventions.md), as long as the section contains the `{mex-entity}` directive
* Links to vocabularies used by the entity
* Note on the `supersededBy` condition, as long as the condition in the Merged schema has exactly the form `"if": {"properties": {"supersededBy": {"type": "null"}}}`

Update by hand:

* Create both `extracted-<entity>.json` and `merged-<entity>.json`. Both must declare the same properties, except for the provenance and identification properties of the Extracted variant and `supersededBy` of the Merged variant.
* Add the conditional `allOf` block for `supersededBy` to the Merged schema (see [Conditional modelling of Merged Entities](entity-conventions.md)).
* Add the entity label and the labels of all its properties to `mex/model/i18n/de.po` and `mex/model/i18n/en.po`.
* Add mapping annotations (`exactMatch`, `closeMatch`, `broadMatch`, `narrowMatch`, `relatedMatch`) where a corresponding concept exists in a standard.
* Add a section to [Entity conventions](entity-conventions.md) with the subsections "When to use", "Common pitfalls", "Schema detail" (`{mex-entity}`) and "Example JSON instances" (`{mex-example}`).
* Add the entity to the overview table in [How the model works](how-the-model-works.md).
* Add the entity to the relevant tables in [Mappings](mappings.md): "MEx-specific extensions beyond DCAT" or "Entity Mapping" for HealthDCAT-AP.
* Add a namespace to the namespaces table in [How the model works](how-the-model-works.md), if a new prefix is used.
* Inform the maintainers of `mex-common`. An example for a new entity is only generated once `mex-common` supports it. Until then, the specification shows a note instead of the example.

When renaming or removing an entity, also remove or adjust all directives, cross-references and table rows that mention it. Otherwise the build fails.

### Adding or changing a field

Updated automatically:

* Schema tables of the field and of all entities referencing it via `$ref`

Update by hand:

* Create or change `mex/model/fields/<field>.json`. Use a lower-case file name, because `{mex-field}` resolves the argument in lower case.
* Add a `{mex-field}` directive to the section "Field Schema Detail" in [How the model works](how-the-model-works.md) for new fields.
* Check the table "Field type constraints" in [Validation rules](validation-rules.md).

A property with the same name must be declared identically in all entities. The schema checks report deviating declarations.

### Adding or changing a vocabulary

Updated automatically:

* Concept table in [Controlled vocabularies](controlled-vocabularies.md), including title and description taken from `concept-schemes.json`
* Links from `useScheme` to the vocabulary

Update by hand:

* Create `mex/model/vocabularies/<vocabulary>.json`. The value of `inScheme` of every concept must be `https://mex.rki.de/item/<vocabulary>`, matching the file name. A mismatch produces a build warning and fails the documentation test.
* Register the concept scheme in `concept-schemes.json`.
* Reference the vocabulary via `useScheme` in the relevant entity schemas.
* Add the vocabulary to the table "Vocabulary list" in [Controlled vocabularies](controlled-vocabularies.md), including the entities that use it.
* Add the vocabulary to the table "Alignment with EU vocabularies and other standards", if it is derived from an external source.

When removing a vocabulary, check that no `{mex-example}` directive refers to one of its concepts or to its concept scheme.

### Adding, changing or deprecating concepts

Updated automatically:

* Concept table of the vocabulary. Concepts are sorted by the numeric suffix of their identifier.

Update by hand:

* Follow the rules in the section "Governance" of [Controlled vocabularies](controlled-vocabularies.md): identifiers are incremented, identifiers of deleted concepts are never reassigned, labels may change while the identifier stays the same.
* Check whether the concept is used in an `{mex-example}` directive with `:identifier:` or in an example in the prose. A removed identifier fails the build.
* Update the matches to external vocabularies, if the concept is derived from an external source.

### Changing mappings to external standards

The conceptual mapping is maintained in two places, which must be kept consistent:

* the mapping annotations in the entity schemas, and
* the tables in [Mappings](mappings.md).

Changes to the interoperability level (A, E or P) of an entity have to be applied to both.

## Maintaining extensions and dependencies

### sphinx-jsonschema

sphinx-jsonschema offers no hooks for customization. `jsonschema_patches.py` therefore replaces the internal methods `_simpletype`, `_kvpairs`, `_cell` and `run` of its `WideFormat` renderer. These methods are not a public interface and may change with any release of sphinx-jsonschema.

When sphinx-jsonschema is updated:

* Run the test suite, in particular `tests/test_docs_jsonschema_patches.py` and `tests/test_docs_build.py`.
* Build the specification and check a rendered entity page: the `useScheme` row with its link, `default` and `pattern` as inline code, and the note on `supersededBy` on a Merged schema.

### Sphinx and MyST

Sphinx is pinned to versions below 9 in `pyproject.toml`. Before raising this limit, check the release notes of Sphinx and MyST for changes affecting directives, `parse_text_to_nodes` and the label registry used by `vocabularies.py`.

### mex-artificial and mex-common

The examples depend on `mex-artificial`, which is installed with the `docs` dependency group. `mex-artificial` depends on `mex-common`, which in turn depends on `mex-model`. During development, uv resolves this dependency to the local project.

This has two consequences:

* Examples are generated from the pydantic models of the installed `mex-common` version. If `mex-common` has not implemented a model change yet, the example may not reflect the current schema or may be missing. Each generated example states the version of `mex-artificial` used in its first line.
* Examples are generated with a fixed seed. They only change when the schemas, `mex-artificial` or `mex-common` change.

After a model release, check that the examples in the published specification match the schemas. If they do not, update `mex-artificial` once `mex-common` has caught up.

### Dependency and template updates

* Renovate opens pull requests for dependency updates. They pass through the same checks as any other change.
* The repository is based on [mex-template](https://github.com/robert-koch-institut/mex-template) and is updated with `cruft update`. The `docs` directory and the workflows are not excluded from template updates. Review changes to `docs/` and `.github/workflows/` carefully after each template update.

## Synchronising local vocabulary copies

MEx keeps local copies of external vocabularies (see [How vocabularies are used](how-the-model-works.md)). Their synchronisation with the upstream source is a manual task. The following procedure is recommended:

1. Record for every derived vocabulary the upstream source and the version or date it was last compared with. The table "Alignment with EU vocabularies and other standards" in [Controlled vocabularies](controlled-vocabularies.md) is the place to document the source.
2. Check the upstream sources regularly and in any case before a major release of the model and after a new release of HealthDCAT-AP.
3. Compare the upstream changes with the local copy. MEx only adopts terms that are relevant in the scope of RKI, so not every upstream addition has to be adopted.
4. Add adopted terms as new concepts with new identifiers, following the governance rules. Do not reuse identifiers of deleted concepts.
5. Handle deprecated upstream terms as deprecations in MEx and check existing metadata before removing a concept.
6. Update the matches to the upstream vocabulary.
7. Document the change in `CHANGELOG.md`, including the upstream version it is based on.

## Roles and responsibilities

| Role | Responsibilities |
| --- | --- |
| Maintainer | Reviews and merges pull requests, starts releases, handles Renovate and template updates, manages repository settings, secrets and GitHub Pages |
| Developer | Changes schemas, fields and vocabularies, maintains the Sphinx extensions and tests, keeps the build free of warnings |
| Metadata specialist | Maintains the prose chapters, vocabularies, mapping annotations and mapping tables, synchronises local vocabulary copies, reviews changes for semantic correctness |
| Maintainers of `mex-common` and `mex-artificial` | Implement model changes in the pydantic models, so that examples can be generated |

## Summary checklist for every pull request

* The change is described in `CHANGELOG.md`.
* `make lint` and `make test` pass locally.
* All manually maintained tables affected by the change are updated (entity overview, namespaces, vocabulary list, alignment table, mapping tables).
* New entities, fields and vocabularies are referenced by the corresponding directive in the specification.
* Translations exist in German and English for all new entities and properties.
* No directive, cross-reference or example refers to a removed entity, field, vocabulary or concept.
